I would lead with app preview and cross-provider continuation. Paired implementations are useful, but the market finding about Cursor means we should sell convenience, not novelty.

1. **Review the running app and send corrections to its agent. Status: absent, with attachment plumbing present.** Current “live preview” means the agent’s terminal, not its web app. Phone images are manually picked, pasted or photographed, uploaded to the PC, and appended as paths to a prompt. Desktop can preview an existing image file. None provides browser capture, element targeting, annotation, app ownership or branch/base comparison. Sources: [terminal preview](C:/Users/ayoub/Videos/claude/loom/src/main.ts:3977), [image attachment implementation](C:/Users/ayoub/Videos/claude/loom/src/remote/images.ts:1), [desktop image viewer](C:/Users/ayoub/Videos/claude/loom/src/main.ts:6116). Small version: associate a reachable app URL with one thread; review it, mark a screenshot and submit that image plus URL, viewport and branch to the selected originating pane. Reuse `upload`, `withPaths`, guarded `submit`. Hardest risk: safely reaching PC localhost from a phone, keeping arbitrary app content away from Loom’s privileged APIs, and retaining correct branch/port ownership. Element inspection and synchronized base comparison are later increments, not cheap additions.

2. **Continue with another provider without reconstructing the task. Status: absent, underlying panes and same-provider resume present.** Existing `messages` supplies only the last prompt and answer, each truncated to 500 characters. That cannot reconstruct decisions. Sources: [message limit](C:/Users/ayoub/Videos/claude/loom/src/main.ts:9151), [resume behavior](C:/Users/ayoub/Videos/claude/loom/src/main.ts:2327), [provider session ID](C:/Users/ayoub/Videos/claude/loom/src/main.ts:1905). Small version: request an explicit handoff brief from the outgoing agent, display an editable objective/decisions/unfinished-work/unknowns draft beside the current diff, stop the outgoing writer, then launch the chosen provider in the same thread. If the provider is unavailable, let the user author the brief. Reuse pane startup, diffs and generation-guarded submission. Hardest risk: omissions presented as recovered knowledge and overlapping writers. Never call this session-state transfer.

3. **Try two implementations against the same checks. Status: absent as a product workflow.** `createThread` already creates isolated branches from a supplied base, but pane count creates multiple panes in one worktree. [Creation](C:/Users/ayoub/Videos/claude/loom/src/main.ts:7056). Small version: pin one commit, create two named threads, submit the same objective with explicit alternative approaches, and run identical user-selected checks in each. Show diffs and results; let the user retain a candidate. Shell receipts already capture exits, but are memory-bound. [Receipts](C:/Users/ayoub/Videos/claude/loom/src/main.ts:8514). Hardest risk: unequal environments and mutable checks producing misleading comparisons. Start from committed code; copying dirty/untracked files is a separate problem. Optional power feature, not the lead differentiator.

4. **Catch up since last visit. Status: absent, adjacent status UI present.** `seen()` clears a waiting flag; it records no reviewed revision or event cursor. Durable task event numbers could provide a cursor. [Seen](C:/Users/ayoub/Videos/claude/loom/src/main.ts:2629), [watch](C:/Users/ayoub/Videos/claude/loom/src/main.ts:9542). Small version: show newly finished tasks, newly changed files and current unanswered questions since an explicit “caught up” action. Check evidence needs additional storage. Risk: turning an agent’s claims into factual progress.
