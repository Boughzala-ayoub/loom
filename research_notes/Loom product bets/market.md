My ranking: **handoff first for personal use; phone preview plus feedback first for public positioning.** Comparison is useful selectively. Fixed teams should remain an experiment.

1. **“Continue with…” across providers.** Frustration: one agent hits its limit or repeats a failed approach, and switching requires reconstructing the objective, constraints, attempts, and current files. First version previews an editable transfer packet containing those items, the worktree, and a concrete next action. Start the receiving session only after the user reviews it; retain the original. This makes Loom’s multiple providers useful within one task. Validate manually on five genuine switches: did the receiving agent start useful work without the user repeating an omitted constraint or correcting the destination? Track repair prompts, not handoff clicks. Public appeal depends on switching being frequent enough; do not imply portable model memory.

2. **Open the actual app from its thread on your phone, then report what is wrong.** Frustration: the agent says a layout is fixed, but the phone shows only its terminal and diff. First version registers one explicit development URL per thread, opens an authenticated phone-accessible preview, and sends a screenshot plus note back to that thread. Add element picking later. Show which worktree/server produced the preview; an attractive screenshot of the wrong branch is actively misleading. Validate with five real UI fixes: can the owner inspect the result and send an actionable correction without returning to the PC? Existing image upload reduces the experiment’s scope. Public story is clear: leave the Windows machine working, inspect the running result elsewhere. Browser tools are established: [cmux documents screenshots, DOM inspection, viewport emulation, console errors, and browser input](https://github.com/manaflow-ai/cmux/blob/main/docs/cli-contract.md). The opportunity is Loom’s complete phone loop, not inventing embedded browsing.

3. **“Since you last looked…” with source links.** Frustration: after lunch, eight panes contain output and it is unclear what changed or needs a decision. First version lists newly completed/failed/unknown tasks, unresolved questions, and changed files since a saved visit cursor. Every entry opens its original evidence. Avoid synthesizing “decisions” from a prompt hash or treating idle as done. Validate by asking the owner to identify all interventions required after three unattended runs; compare omissions and time against today’s Overview. Strong personal utility, weaker reason for a stranger to switch products. This can support either leading feature.

4. **Two implementations, one acceptance test.** Worth trying for ambiguous changes, poor default for ordinary work. Fix the base revision, objective, and independently defined checks; run two isolated candidates and show checks, diffs, and runnable results. Human chooses; no automatic merge or judge score. [Cursor already documents `/best-of-n` across models with isolated worktrees and comparison](https://cursor.com/docs/configuration/worktrees). Loom must earn its place through usable local CLI sessions and review from the phone. Test on three difficult real tasks using existing panes before building UI. Keep it only if the second result changes the user’s choice enough to justify extra running and review time.

5. **Fixed builder/reviewer/checker workflow.** Prototype through loomctl, not a workflow designer. One builder edits; reviewer reports against a captured revision; checker executes a fixed command; builder receives accepted findings for one repair round. [Anthropic documents coordination overhead, greater token use, file conflicts, and resumption limitations](https://code.claude.com/docs/en/agent-teams). Treat extra agents as a cost that must produce value. Compare three runs against the owner’s current operator workflow. If manual interventions do not fall, do not productize it.

**Missed candidate: “Ask another agent to challenge this approach.”** This is a smaller, stronger first experiment than a permanent team. Transfer the objective, constraints, and selected evidence to a second provider for a bounded review, then let the user send chosen findings back. It reuses handoff work and supports concrete stop-and-rethink moments. Measure findings the owner accepts and subsequent rework, not generated criticism.

No implementation or runtime checks performed. Rankings are product judgments; public demand remains unvalidated.
