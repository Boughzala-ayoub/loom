# Loom product and implementation research

## What does Loom already do?

### Takeaway
Loom already covers most of the day-to-day mechanics of supervising local agents. The strongest additions connect starting a worktree, reviewing the result, and deciding whether it is safe to land. Public-product work also needs a usable first launch and a supported delivery path.

### Cited Findings
- Research snapshot is local HEAD `ac726f7`, read on 2026-10-11. Source inspection, README, prior study and recent git history were used. No app launch or runtime verification was performed. Filesystem links below point to this checkout.
- Windows-only Tauri/WebView2 and ConPTY workspace, grouped worktree threads and up to 16 panes, with agent sessions restored across launches. Main agents documented are Claude, Codex and OpenCode, with custom startup commands too. [README](../../README.md:1), [thread creation](../../src/main.ts:7056), [opening/restoring panes](../../src/main.ts:5695), [startup commands](../../src/main.ts:9176).
- Waiting-agent management is already substantial: Overview, status filtering, search, last user/agent messages, groups, bulk prompts, live previews, replies and menu choices with change detection. Proposing an agent dashboard, command palette, broadcast or approval inbox as wholly new would duplicate existing work. [README](../../README.md:98), [waiting cards](../../src/main.ts:3922), [replies](../../src/main.ts:5096), [menu choices](../../src/main.ts:5126), [bulk selection](../../src/main.ts:5169).
- Phone control is already a separate four-tab web app through Tailscale: agents, Git Changes, usage and settings. It includes pairing, Web Push, dictation, image attachment, remote keyboard and restart controls. [README](../../README.md:256), [remote backend](../../src-tauri/src/remote.rs:1), [images](../../src/remote/images.ts:122), [settings](../../src/remote/settings.ts:270).
- Git coverage includes file/hunk stage, unstage and discard, commits and push, branch switching, stashes, merge/rebase recovery, file viewer, commit history and guarded worktree deletion with trash. These are mature enough to extend, but the many recent deletion fixes show that destructive orchestration deserves more than a superficial estimate. [README](../../README.md:314), [Git command entry](../../src/main.ts:8974), [deletion inventory](../../src/main.ts:5773), [worktree/branch locking](../../src-tauri/src/deletion.rs:183), [trash guide](../../docs/loomctl.md:342).
- Create PR pushes the captured branch and opens GitHub's compare form. It does not create a PR through an API, retain a PR identity, fetch CI checks or fetch review comments. GitHub is the only supported host in this action. [PR creation](../../src/main.ts:6933), [PR URL and push](../../src/main.ts:6945).
- Dictation is local whisper; plan usage and context reads already exist. Do not propose these as additions. [README](../../README.md:365), [usage/context](../../README.md:424), [phone usage](../../src/remote/usage.ts:70).
- loomctl has durable task IDs, idempotent submissions, receipts, event watching, correlation/uncertainty reporting and CLI history. It keeps every open task and the last 500 finished tasks. The ordinary Overview is a live pane view, not a historical task browser. [task states and meaning](../../src/task.ts:1), [submit](../../src/main.ts:9334), [task/history commands](../../src/main.ts:9510), [retention](../../src/main.ts:4485).
- Task records deliberately store prompt hashes and lengths rather than prompt text. A persistent queue of future prompts changes the existing storage/privacy design. [Task fields](../../src/task.ts:158).
- Workspace snapshots already have backups and replacement writes; don't pitch basic workspace backup as missing. [workspace loading/saving](../../src-tauri/src/lib.rs:1787).

### Inferences
- Loom's advantage is the combination of local Windows agents, safe input routing and phone supervision. Expanding the IDE/editor portion is less directly connected to that advantage than shortening the start-review-finish cycle.
- "Agent completed" must remain distinct from "the code passed checks." Existing task completion is correlated to agent turns or shell commands; it does not attest to the quality of a patch.

### Gaps
- Static inspection cannot prove every documented behavior works in the installed build.
- There is no user telemetry, adoption funnel, support volume or interview evidence in this investigation. Demand and time savings are hypotheses.

## Which opportunities fit personal use and a public product?

### Takeaway
For personal use, start with review comments and repeatable worktree setup, then explicit local checks. For a public product, first-launch checks and update delivery precede broad feature expansion. Keep a separate public PR/CI bet even though the earlier personal study parked it.

### Inferences
- Proposed personal sequence: diff notes, setup, local checks, base/overlap, then choose Land or durable next-task based on observed interruption cost. Land and queues should not be rushed merely because their happy paths are short.
- Proposed public sequence: first-run checks and supported releases, then setup plus diff notes plus clear check evidence. Test PR/CI with a few external Windows users before investing in issue import or cross-host integrations.
- Historical tasks is a useful smaller release between larger changes. It makes existing durable data visible without adding another orchestration system.
- Feature success can be measured manually in a small pilot: time to first agent prompt, time from a review observation to a submitted fix request, number of worktrees requiring manual setup repair, and ability to identify exactly which revision passed which check.
- Defer cloud runners, multiplayer, full editor/browser replacement and a generic automation graph. They add operational or compatibility work beyond the next useful increment. This is a scope recommendation, not a permanent user veto.

### Gaps
- Demand for PR/CI and issue import needs public-user evidence. Repository implementation only establishes feasibility.
- No development estimate was validated by a prototype. Shipping also requires the user's desktop and phone viewport checks, security checks appropriate to new boundaries, and failure/restart tests.
- Actual installed signing status and any external release infrastructure were not inspected; the conclusions above concern this checkout and README.

## What changed since the earlier study?

### Takeaway
The October 6 study remains useful background, but many recommendations are still proposals and several maintenance gaps have since been addressed. Treat its personal-workflow assumptions as dated rather than as permanent product rules.

### Cited Findings
- Prior study identifies setup, per-thread ports, local Land, base/overlap, diff comments, task dependencies, usage-reset scheduling, stuck detection and shell logs. Our repeated items are continuations, not newly discovered ideas. [prior study](../../docs/improvement-study.md:1).
- `npm test` is present, and the prior study's detailed section itself was updated to say it was done. Async cli_reply/cli_ready were also committed as `da0b23c`. Do not carry the prior short-summary wording forward as current gaps. [package scripts](../../package.json:9), [prior completed items](../../docs/improvement-study.md:239), [native command handling](../../src-tauri/src/control.rs:299).
- Branch drift has a partial implementation: syncBranch re-reads the symbolic branch before status, PR and deletion. It does not supply the missing original base or cross-thread file warnings. [branch synchronization](../../src/main.ts:5756), [status](../../src/main.ts:6964).
- Recent commits add phone images `b4e9e20`, agent image submission `a28e005`, longer upload/transcription handling `f76e8a5`/`f5c7461`, phone Changes folding `3fb97a9`, commit history pagination `2e5b4a9`, and OMP visual identity `078eef3`/`f9add5b`/`ac726f7`. [current phone attachment code](../../src/remote/images.ts:122), [paginated Git status](../../src/main.ts:6964), [current README phone coverage](../../README.md:273).
- Many recent commits harden branch deletion against concurrent checkout, Git locks, junctions, relative gitdir paths and core.worktree. Local Land/cleanup would interact with exactly those conditions. [deletion implementation](../../src-tauri/src/deletion.rs:92), [recent review archive](../../docs/reviews/LOOM_CORE_WORKTREE_GAP_FIX_CODEX_REVIEW_2026-10-10_043120.md).

### Inferences
- Distinct additions in these notes relative to the previous study are revision-bound local check evidence, a historical task UI, first-launch/doctor workflow and supported release delivery. PR/CI becomes relevant again under the user's explicit public-product objective.
- Phone image delivery is shipped; it should become part of onboarding/demo material rather than a fresh roadmap item.
- Low-output detection should be framed as "no observed progress," never definitive "stuck." Quiet reasoning, long tests and tool calls can all be legitimate. This remains a secondary candidate behind explicit task/check visibility.

### Gaps
- I did not inspect session history or competitors, as those are assigned to other researchers. Earlier study claims about user preferences are not independently verified here.
- No source changes or tests were needed for this study; runtime behavior and the installed bundle remain unchecked.
