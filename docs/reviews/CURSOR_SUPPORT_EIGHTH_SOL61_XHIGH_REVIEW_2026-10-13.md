## 1. The approval fallback timer ignores an active report hold

`cursorQuestion`'s one-second callback (`src/main.ts:2592`) calls `cursorAsks` while `reportsHeld` still queues the pane's events in `agentEvents` (5168). `cursorAsks` uses the last processed `cursorGen`.

A starts at 1000, and Loom already knows `gA`. At 2000 a real Esc goes out through `p.sending` and reaches Cursor, but its successful acknowledgement is delayed. A is interrupted at 2060. B's Enter goes in at 2090, its start is written at 2110, and its real approval draws at 2140. At 2250 `agentEvents` receives A's interrupt and B's start, and the Esc's report hold queues both. The page stays responsive. Running its timers to 3200 fires the fallback at 3140, with `cursorGen` still `gA`. At 3500 the Esc's successful acknowledgement arrives, with the native writer's start at 2000, and `p.wrote` releases the held reports.

A ends cancelled, but its history is accepted, submitted, working, approval, cancelled, and it keeps B's question as its detail. B is correctly in approval, but the notices are `[approval, approval]`. A should have no approval event and no copied question, and only B's real approval should raise a notice. This isn't the documented limit for a page stalled longer than a second. This page responds, and B's start has already arrived, but the new stop-write hold keeps it back.

The fresh served-bundle check uses real terminal key input. It delivers the mocked native write's success, holds only its acknowledgement, sends the report batch and waits 1200 ms. It makes two correlated manual tasks with the same wrong approval on A, and no page errors. It doesn't show how often a live account hits this.

While a stop's write still holds the events that establish the current turn, the fallback shouldn't give the question to an older known turn. The approval should wait visibly at once and be reconciled when the hold releases. The genuine queued-follow-up case must keep working: with no newer start, when A itself asks, A must still move to approval once the write's outcome is known. Returning from the timer while a hold exists isn't enough, since the approval would be lost for good if the released batch has no start, so that protection needs a check too. Both stop orders, failed writes, errors written before the native writer began, noted manual Enters and submitted tasks, late stops, and one notice per real approval must keep working.

## 2. An old answer's acknowledgement updates a restarted pane's task

`sending` (`src/main.ts:3015`) records the menu and an optional stop but not the pane's launch. `wrote` (3038) updates the current pane, and `taskSignal` (3069) sends the resume without the original launch. Both writers need reading, the terminal's key handler (2249) and the shared `keys` (4238), with their follow-up effects, failures and release paths.

A starts in pane generation 1 at 1000 and asks the shell approval at 2000. At 3000 y goes out and reaches that process, but its acknowledgement is held. The same `Pane` object relaunches: the fields that a production launch resets are reset, the old task is swept away, and B starts in generation 2. B asks the same menu revision at 3500. At 4000 the old y's acknowledgement calls `p.wrote` with its recorded menu, and activity reads the unchanged new menu.

B should stay in approval with `cursorAsking` true. Instead B works, `cursorAsking` turns false, and the identical question stays suppressed as `cursorAnswered`, though no answer went to the new process. The old acknowledgement sends its resume on the current generation, so it changes the new task's saved history.

The served-bundle check uses the real CLI restart path through Tauri's mocks. It sends y to generation 1 and holds that successful acknowledgement, then calls `restart --yes`. B starts in generation 3, because stop and spawn each increment the generation, and the identical approval draws. Before the old acknowledgement is released, B is in approval. After, B works, with a false answered event. There are no page errors. In this test the pane's unread alert and the four Overview choices survive, so it doesn't prove hidden controls. The failure it shows is the wrong task state and the wrong answered menu.

The input's meaning and its acknowledgement should be bound to the pane generation it was typed in. A late success or failure must not change a newer process's question, task, `answerInDoubt`, interruption state or attention. The write's own holds must still be released, so queued reports go on. The fix belongs in the shared input path and the terminal callback's extra effects, not only in this test, and not as a launch on the resume alone while other changes still reach the new process. Delayed acknowledgements in the current generation, immediate replacement approvals and same-menu redraw suppression must keep working. The checks should cover a late answer's success and failure and a stop write's late acknowledgement and release, keeping real delivery outcomes and the launch protection for other agents.
