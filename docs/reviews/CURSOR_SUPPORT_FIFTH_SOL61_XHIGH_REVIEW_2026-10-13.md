## 1. A delayed start report hides an unanswered approval

`agentReport` (`src/main.ts:5095`) calls `cursorRuns(true)` on a start, and `cursorRuns` (2958) clears `waiting` unconditionally (2960). `cursorQuestion` (2569) returns at 2575 when the menu's presence equals `cursorAsking`. A `taskSignal` approval can't move a submitted task to approval before the start ties the task to its turn, because `route` sends an approval only to working tasks.

The case fits one normal 250 ms poll interval. After a poll at 1950, A's Enter goes in at 2000, Cursor writes A's start at 2020 and draws its shell approval at 2140. Before the next report poll, `p.activity()` reads the real approval, sets `cursorAsking` and `waiting`, and signals the approval, but the task is still submitted, so nothing moves. At the 2200 poll `agentReport` handles the start, `cursorRuns(true)` clears `waiting`, and `taskSignal` makes the task working. Later activity sees the same menu and returns without asking again.

The actual `[cursorAsking, busy, waiting, task.state, notices]` is `[true, false, false, working, []]`, where `[true, false, true, approval, [approval]]` is expected. The pane is blocked but shows idle, its approval buttons are gone from the Overview and the phone, and its task's approval notice never goes out.

A focused headless check of the served production bundle confirms the effect in the UI (`cursor-fifth-ui-repro.mjs`, `cursor-fifth-ui-repro.json`). The four approval buttons go to zero, `panes` reports the pane idle and `tasks` reports the task working, while `menu` still returns the same four choices. `early-approval-before-320.png` and `early-approval-after-320.png` show the change. That check holds the start report back on purpose, to look before and after. The production-method fixture proves the 250 ms timing case. It uses Tauri's official mocks, with no real terminals, Git or account calls, and no page errors occurred. It expects the choices to survive, so it fails now with `0 !== 4`.

The fix should keep an outstanding menu's `waiting` when the start is handled, and apply the approval to the task the start just tied to the turn. The task notice and the usable choices must come back, without a second approval notice. Ordinary starts, answered approvals and immediately queued approvals must keep working. Keeping `waiting` alone would still leave the task wrongly working.

## 2. Ctrl-C in rejection feedback hides a later genuine failure

`Pane.wrote` (2991) checks only `!cursorAsking` before it records interruption times (2994, 2996), and `agentReport` turns a later failure into an interrupt (5105).

A starts at 1000 and its shell approval appears at 3000. Esc on the approval at 4000 opens Cursor's rejection feedback, and `answeredCursor` clears `cursorAsking`. The feedback screen is a plain input, so `readMenu` doesn't see a question. Ctrl-C at 5000 skips the feedback, and the generation goes on in Cursor. Loom sees no question, so it records an interruption for `gA`. A genuine error in that generation at 60000 then becomes an interrupt.

The actual `[task.state, waiting, notices]` is `[cancelled, false, [approval]]`, where `[failed, true, [approval, failed]]` is expected. The user loses the real failure notice.

The evidence comes from the installed Cursor CLI 2026.10.01-e373342, in `C:/Users/ayoub/AppData/Local/cursor-agent/versions/2026.10.01-e373342/7671.index.js`. Its Ctrl-C handler (around line 332412 of the formatted file) handles `rejection-reason` by calling `Xe`, the `onSkipRejectionReason` callback, and resetting the input. It returns before the separate generation abort handler `Te`. The callback (around line 799951) rejects the pending decision through `un`. `rejectDecision` (around line 686239) resolves that decision with `approved: false` and removes it, without aborting the generation. A feedback skip and a real Ctrl-C turn stop are therefore different events. The review used the production-method reproduction and these CLI handlers, not a live Cursor account turn.

The fix should tell a feedback response apart from a turn interruption, so that skipping feedback doesn't poison the generation's later stop. Genuine Esc and Ctrl-C cancellation must keep working. So must accepting, rejecting and leaving the feedback, early and overlapping cancellations, both stop orders, and late errors routed to their own turn. Turning cancellation detection off everywhere, or only changing a scratch expectation, doesn't fix it.
