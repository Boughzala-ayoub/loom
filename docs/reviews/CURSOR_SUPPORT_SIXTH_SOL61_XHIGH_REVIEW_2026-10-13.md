## 1. An older turn inherits the newer turn's approval

`agentReport` (`src/main.ts:5141`) now calls `cursorAsks` (2593) after each start. `agentEvents` (5088) handles a batch's reports one at a time.

The case fits one normal 250 ms poll interval. After the poll at 1950, A's Enter goes in at 2000, its start is stamped 2020 and it completes at 2060. B's Enter goes in at 2090, its start is stamped 2110 and its approval draws at 2140. Both tasks are still submitted when activity reads B's real approval. The poll at 2200 brings start A, end A and start B, in that order. The call after start A applies B's visible menu to A. End A then completes A, and start B correctly applies the menu to B.

A's history is accepted, submitted, working, approval, completed. B is in approval, and the notices are `[approval, completed, approval]`. A should have no approval event and no copied approval detail, B should be in approval with one approval event, and the notices should be `[completed, approval]`. The wrong approval goes into A's saved history and sends a false approval notice. A's completed task also keeps B's question as its detail. On `e57f401`, A gets no false approval. B's missing approval there is the older fifth-review bug, so the wrong A event is a regression on its own.

The served bundle shows the same wrong A history with one real `agent-events` batch and two separately correlated manual tasks, while B's pane still waits (`cursor-sixth-batch-ui-repro.mjs`, `cursor-sixth-batch-ui-repro.json`, rebuilt by `make-cursor-sixth-batch-ui.cjs`). The fix should apply a live menu to the current turn's task, not to every historical start the poll replays. Applying it once, after the batch has established the current turn, is one small way. The original single early-approval case must keep working, as must answered and seen approvals and one notice per real task approval. If reconciliation moves to a batch boundary, the fixture should call that real entry point rather than weaken its expected outcomes.

## 2. A redraw before the acknowledgement still hides genuine failures

`Pane.wrote` (3008) checks the live `cursorAsking` and `cursorFeedback`, and `cursorQuestion` clears `cursorFeedback` (2578). Terminal input (around 2249) and the shared `keys` helper (around 4189) both classify the answer before they call `pty_write`, but call `wrote` only after its Promise resolves.

A starts at 1000 and asks for a shell approval at 3000. Esc at 4000 opens its rejection feedback. The fixture draws Cursor's real placeholder, `  → Tell the agent what to do instead (Enter to send, empty to skip, Esc to cancel)   ctrl+c to stop`, and activity sets `cursorFeedback`. At 5000 Ctrl-C goes in while the feedback is open. Cursor skips the feedback and draws its "Add a follow-up" composer before the native write's acknowledgement reaches the frontend, so activity clears `cursorFeedback`. At 5001 `wrote` sees neither a menu nor feedback and records an interruption for `gA`. A genuine error in that generation at 60000 then becomes the interrupt.

The actual `[task.state, waiting, notices]` is `[cancelled, false, [approval]]`, where `[failed, true, [approval, failed]]` is expected. The real failure alert is lost. The production-method test asserts that the feedback was recognized before the key and cleared by the redraw before the acknowledgement, so this isn't a missing fixture or parser dependency.

The native writer sends its result after `write_all` and `flush` on its own thread (`src-tauri/src/lib.rs` around 573 to 584). A separate reader thread delivers Cursor's redraw (around 597 to 614), and `pty_write` awaits the writer's result (664). Nothing orders the JavaScript write result before that independent output. A fresh headless check of the served bundle delivers the redraw before a held Tauri write acknowledgement (`cursor-sixth-ui-repro.mjs`, `cursor-sixth-ui-repro.json`). After a genuine failure it shows the task cancelled and the pane idle, with no page errors. That controls the ordering. It doesn't measure how often a live account hits it. The same failure exists on `e57f401`.

The fix should decide whether a key interrupts the turn or answers a menu or the feedback before the asynchronous write, and carry that through the acknowledgement. Both writers and their failed and uncertain writes need reading. What a delivered key meant shouldn't be decided from a screen that key already changed, and real Ctrl-C cancellation must keep working everywhere.

## 3. Skipping the feedback leaves the task stuck in approval

`answers` (2956) leaves Ctrl-C out, and `wrote` returns at 3017, before the resume `taskSignal` at 3022, when the answer is false.

This case has no acknowledgement race. A asks, Esc opens the feedback, and activity recognizes it. Ctrl-C goes in and is acknowledged before the redraw, and Cursor skips the feedback and works on in the same generation. `wrote` clears the feedback, but `answers` said false for Ctrl-C, so no resume goes out. After the "Add a follow-up" redraw, `[task.state, busy, waiting]` is `[approval, true, false]`, where `[working, true, false]` is expected. The task claims to wait for approval while its pane works. Rejecting the pending decision starts no new prompt, so no later start repairs it.

Empty Enter in the same feedback input makes the same rejection in Cursor and resumes the task correctly. Its protection case gives `[working, true, false]`. In the installed Cursor CLI 2026.10.01-e373342 (`C:/Users/ayoub/AppData/Local/cursor-agent/versions/2026.10.01-e373342/7671.index.js`), Ctrl-C in `rejection-reason` calls `onSkipRejectionReason`. That callback rejects the pending decision and clears the rejection id and the input, without aborting the generation. The `rejection-reason` submit handler makes the same rejection with an undefined reason for an empty Enter. These handlers sit near byte offsets 332381, 799951 and 797557 of the minified file, and `node_modules/.cache/review/cursor-sixth-feedback-handlers.cjs` prints them.

The served-bundle check with a normal acknowledgement (`cursor-sixth-ui-repro.mjs --normal-ack`, `cursor-sixth-ui-repro-normal-ack.json`) shows the task still in approval after the skip while the screen shows "Add a follow-up". In this order a later genuine failure correctly fails, so the missing resume is separate from finding 2. The gap also exists on `e57f401`.

The fix should treat a real feedback skip as a resume, as an empty Enter already is, while Esc's return to the approval keeps it asking. Text feedback, the approval's own choices, real turn cancellation, and failed writes that leave the question outstanding must keep working.
