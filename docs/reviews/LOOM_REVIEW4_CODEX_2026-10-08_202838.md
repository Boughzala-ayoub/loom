1. **P1. CLI deletion can choose a different branch from its approved plan or current worktree.**

Locations: [closePlan, main.ts:8428](C:/Users/ayoub/Videos/claude/loom/src/main.ts:8428), [close-thread, main.ts:9633](C:/Users/ayoub/Videos/claude/loom/src/main.ts:9633), [removeThread, main.ts:5841](C:/Users/ayoub/Videos/claude/loom/src/main.ts:5841). The CLI checks the plan, then calls `removeThread` with `ask=false`. That helper captures the current mutable `th.branch`, rather than the branch captured in the plan.

Reproduced with the actual `closePlan`, CLI command handler, `inventory`, `syncBranch`, and `removeThread`, real Git, and the actual native fingerprint. The approved plan named `approved`. During the recheck's asynchronous SHA-256 calculation, after the inventory and target were captured, I switched the worktree to `unapproved` at the same commit and ran `syncBranch`. The digest still matched the approved plan. The command reported success and deleted `unapproved`; `approved` remained. The hook wrapped the real digest function and inserted the other Git operation before its caller resumed.

A second real-Git case needs no hash timing. Switch the worktree to `unapproved` while its cached branch remains `approved`, then run the actual CLI handler with `--delete branch --yes --force`. `--force` skips `closePlan` and branch synchronization. It deletes cached `approved` and keeps checked-out `unapproved`.

Fix: build a deletion plan's branch from its inventory, pass that approved branch explicitly into `removeThread`, and read Git's current branch before choosing a target when no plan is checked. Add both CLI regressions. Without this, CLI deletion can still remove a branch outside the approved plan or target the wrong branch after a terminal switch.

2. **P2. A failed fetch becomes a successful thread from the wrong base.**

Locations: [resolveBase, main.ts:6999](C:/Users/ayoub/Videos/claude/loom/src/main.ts:6999), [createThread fallback, main.ts:7025](C:/Users/ayoub/Videos/claude/loom/src/main.ts:7025). Any fetch rejection becomes `null`, which the caller treats as a request to create a new branch from local HEAD. A failed lookup does not establish that the remote branch is absent.

Reproduced with an origin containing a feature-only commit and a single-branch main clone. I renamed the temporary origin directory to simulate an unavailable remote. Real Git reported that it could not read the remote repository. The actual `createThread` nevertheless returned success, created branch `feature`, and checked out local main's commit `5be965b`, rather than feature's `d054879`.

Fix: propagate transport, configuration, and permission failures. Only take the new-branch fallback after establishing that the named ref is absent. Preserve the intentional new-branch behavior for a genuinely missing name and repositories without an origin. Otherwise an unavailable remote silently starts an agent on unrelated code.

3. **P2. The fetched commit loses its only ref before worktree creation consumes it.**

Locations: [early cleanup, main.ts:7002](C:/Users/ayoub/Videos/claude/loom/src/main.ts:7002), [consumer, main.ts:7058](C:/Users/ayoub/Videos/claude/loom/src/main.ts:7058). `resolveBase` deletes its private ref before returning the commit. Several awaits precede `git worktree add`, leaving that commit without the ref created to protect this operation.

Reproduced with real Git and the actual `createThread` in a single-branch clone. I seeded an unreferenced feature commit from an earlier fetch and set its loose-object timestamp to 40 days ago to model an old repository. The operation's fetch did not refresh that timestamp. Immediately after the helper deleted its private ref, another fetch replaced `FETCH_HEAD` with main, then ordinary `git gc --quiet` ran. It pruned feature commit `84c56ce`; `worktree add` failed with `not a valid branch point`. No `--prune=now` or altered prune configuration was used.

Fix: retain the private ref until the new branch and worktree have been created, and release it from the creation operation's final cleanup. Otherwise routine garbage collection can break creation from previously fetched, old objects despite a successful fetch.

4. **P2. Phone and CLI stash actions reject full SHA-256 identities.**

Locations: [stashCommit, stash.ts:28](C:/Users/ayoub/Videos/claude/loom/src/stash.ts:28), [CLI drop, main.ts:9035](C:/Users/ayoub/Videos/claude/loom/src/main.ts:9035), [phone identity, remote/changes.ts:337](C:/Users/ayoub/Videos/claude/loom/src/remote/changes.ts:337). The native command accepts 40- and 64-character commit identities, but `stashCommit` recognizes hex identities of at most 40 characters.

Reproduced in a real repository initialized with `--object-format=sha256`. The stash list returned a full 64-character SHA. The actual CLI stash-drop handler rejected that SHA with `No stash ... in the list now`, made zero native calls, and left the stash intact. Calling the compiled native `stash::drop` with the same SHA succeeded. The phone passes this full SHA into the CLI path; stash apply uses the same resolver.

Fix: accept full SHA-256 identities and prefixes while preserving ambiguity checks between distinct commits. Otherwise the phone's listed stash actions fail in these repositories, and CLI users must know to truncate a valid full SHA.

5. **P3. A full stash SHA is falsely called ambiguous when the same commit is stored twice.**

Location: [stashCommit, stash.ts:31](C:/Users/ayoub/Videos/claude/loom/src/stash.ts:31). Ambiguity is counted by list entries rather than distinct matching commit identities.

Reproduced with real stashes A and B, followed by `git stash store -m 'second copy' <A>`. The list contained A, B, A. The actual CLI handler rejected A's full 40-character SHA with `More than one stash starts with ... Give more of its commit.` No longer SHA can solve that error. The native command accepted A and removed its newest matching entry, leaving B and the older A.

Fix: deduplicate matching SHAs when testing prefix ambiguity and keep entry selection under the native lock. Otherwise valid full-SHA actions fail on duplicate entries, including phone selections, with an impossible recovery instruction.

6. **P3. Failed private-ref cleanup is hidden and leaves a permanent ref.**

Location: [suppressed cleanup failure, main.ts:7002](C:/Users/ayoub/Videos/claude/loom/src/main.ts:7002). The helper discards every `update-ref -d` error and returns success.

Reproduced by holding the just-created operation ref's standard Git `.lock` file while cleanup ran. Real Git rejected deletion with `cannot lock ref`. The actual `createThread` returned a correctly based worktree without surfacing the cleanup failure. After I released the competing lock, `refs/loom-fetch/f3f14a79-98ac-49f2-8df7-ef271a6c636b` still existed. Nothing retries or reports its cleanup.

Fix: retry transient contention within a bound, then report the owned ref and cleanup failure if deletion still fails. Do this after the lifetime fix in finding 3. Otherwise leaked refs can keep old commit histories reachable after the corresponding threads are removed.
