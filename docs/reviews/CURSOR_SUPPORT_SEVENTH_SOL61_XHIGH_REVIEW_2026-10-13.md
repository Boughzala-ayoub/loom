## 1. A turn Loom already knows takes the next turn's approval

`cursorAsks` (`src/main.ts:2595`) names `this.cursorGen`, and `cursorQuestion` calls it from activity, before the next report poll. The batch step in `agentEvents` (5111) can't undo an approval that screen read already attached.

A starts at 1000, and Loom has read its start, so `cursorGen` is `gA` and A's task works. After the 1950 poll, A completes at 2060, B's Enter goes in at 2090, and B's start is written at 2110. B's approval draws at 2140, before the 2200 poll reads A's end and B's start. Activity reads B's real menu while `cursorGen` is still `gA`, and `cursorAsks` attaches it to A. The next batch correctly completes A and starts B into approval, but A's wrong event and notice are already recorded.

A's history is accepted, submitted, working, approval, completed, with B's question kept as A's detail. B is correctly in approval, and the notices are `[approval, completed, approval]`. A should have no approval event and no copied detail, B its own approval, and the notices should be `[completed, approval]`. The wrong event sends a false approval notice and corrupts A's history.

This differs from the sixth-review case, where A's start was still unread. There A's start had been read in an earlier poll, so moving the approval after the batch can't stop the earlier screen read from using that known turn. The case also occurs on `a6d8c8b`. A fresh served-bundle check starts A first, then withholds A's stop and B's start while B's menu draws. It makes two separately correlated manual tasks with the wrong approval on A, and no page errors.

The last reported turn id isn't proof that a new approval belongs to it while a newer submitted prompt waits for its start. The fix should defer the task association in that gap and reconcile it with the newer start, while the pane's approval shows and waits at once. It should cover submitted tasks and noted manual Enters, not one route only. Genuine current-turn approvals, queued follow-ups, late stops, early approvals before any known start, and one notice per real approval must keep working.

## 2. A late acknowledgement hides the replacement approval

`answeredCursor` (2991) reads the menu on screen at the acknowledgement and stores its revision as `cursorAnswered`. `wrote` calls it (3033) for a response captured earlier only as a boolean.

A starts at 1000 and asks menu 1 at 3000. At 4000 the user answers it with y, Tab, Enter or Ctrl-C, and `answers()` correctly says it's a response. Cursor handles the key and draws menu 2 at once, with `echo next` instead of `echo hi` and a different `menuRev`, before the asynchronous `pty_write` acknowledgement arrives. Activity sees a menu still present and `cursorAsking` still true, so it returns. At 4001 `wrote` calls `answeredCursor`, which reads menu 2 and marks that newer menu answered. It then resumes the task and clears the alert.

`[cursorAsking, busy, waiting, task.state]` is `[false, true, false, working]`, with `cursorAnswered` set to menu 2's revision. It should be `[true, false, true, approval]`, with menu 2's question as the detail. Later redraws of the same menu keep returning at `cursorQuestion`'s `cursorAnswered` check, so it never repairs itself. The task claims to work while Cursor waits on the second approval.

All four keys fail the production-method check. On the served bundle, `loomctl menu` still offers the replacement menu, but the Overview shows no approval buttons and the task and pane report working, with no page errors (`cursor-seventh-replacement-375.png` shows the hidden options). The y, Tab and Enter cases also fail on `a6d8c8b`. Its Ctrl-C capture differs, as expected for a commit before the resume fix, but it still suppresses the replacement menu.

The fix should capture which menu is answered, its identity and revision, before the write, not only a boolean. Acknowledging menu 1 must neither suppress menu 2 nor clear its alert, and the task should stay in approval with the new question and its own notice. Both the terminal's key handler and the shared `keys` and `choose` paths need reading. Failed writes, queued approvals, the revision guards, Tab and Shift+Tab choices and the usual suppression of a same-menu redraw must keep working. One write's snapshot must not be overwritten by another write in flight.

The last fix report mentioned that Esc rejects MCP, Delete and Read approvals instead of asking for feedback. The fix should check Cursor's real behavior for those approvals while it fixes the shared response handling, and not keep assuming that every menu's Esc opens feedback. The shell approval's Esc to feedback and the feedback's Esc back to the approval must keep working. A directly related correction the code proves belongs in this fix, with a concrete regression.

## 3. A real Esc can be reported as a failure

`wrote` (3014 to 3019) records the interruption only after `pty_write` resolves. `agentReport` (5115 to 5118) marks the first stop seen in `turnsSeen` before it classifies the stop, and checks `cursorEsc` at 5140 and 5141.

A starts at 1000. At 2000 Esc goes in while A works, and `answers()` correctly says false: this is a real turn stop, not a menu or feedback response. The native write goes in, and Cursor writes its usual cancellation error at 2010 and aborted at 2020, both for `gA`. The 2250 poll delivers both stop files before the successful `pty_write` acknowledgement reaches the frontend at 2300. `cursorEsc` is still empty when the error arrives, so A fails and raises a failure alert. `turnsSeen` then drops the aborted. The later `wrote` can't repair A, which is already final, and whose turn has already used its stop.

`[task.state, waiting, notices]` is `[failed, true, [failed]]`, where `[cancelled, false, []]` is expected. With aborted first, the passing protection case already cancels. The same delivered real Esc must cancel in both orders, as it does when the acknowledgement comes first. The case also fails on `a6d8c8b`.

The served-bundle check delivers a successful Esc write through the Tauri mocks and holds only its acknowledgement. It emits the failure and then the interrupt, and releases the acknowledgement. The task stays failed and the pane waits, with no page errors. That controls a valid asynchronous order. It doesn't measure how often a live account hits it. The native writer's result and the native output and report delivery take independent paths.

The fix should settle the pending interruption and its delivery before it finalizes the stop that the interruption may explain. It should keep the generation and timing needed to classify the stop correctly, instead of stamping the interruption only when its acknowledgement arrives. It shouldn't reinterpret a journal event that's already final after a false failure notice went out. It also shouldn't take the request time as the delivery time, since writes can queue or fail. Delivered-key order, genuine errors written before an Esc, failed and uncertain writes, both stop orders, early cancellations and a newer generation's genuine error must keep working. Report classification and duplicate suppression need reading as well as both input writers. Holding an already classified `taskSignal` after `agentReport` has used its stop isn't enough.
