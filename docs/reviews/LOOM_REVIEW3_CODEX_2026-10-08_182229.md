## Findings

### 1. P1: the desktop deletion dialog can delete a branch the user never approved

Location: `src/main.ts`, `Inventory` and `inventory()`, `inventoryDiff()`, the confirmation and its recheck in `removeThread()`, and the `git branch -D` after them.

The first inventory runs `syncBranch`, and the dialog names `th.branch`. While the dialog is open, an agent can switch the worktree to another branch at the same commit. The second inventory runs `syncBranch` again and changes `th.branch`, but neither `Inventory` nor `inventoryDiff` holds the branch. HEAD, the counts, the file and index fingerprint and the status can all stay the same, so the recheck passes. Deletion then runs `git branch -D` with whatever `th.branch` says by then.

Reproduced case: a repository with `main`, a linked worktree on branch `approved`, and a branch `unapproved` at the same commit. The actual `removeThread`/`inventory` path asks "Delete the worktree AND the branch approved?". Before the confirmation returns true, the worktree switches to `unapproved`. The native worktree fingerprint doesn't change. The recheck passes, Loom removes the worktree and deletes `unapproved`, and `approved` is still there. No uncommitted files or unique commits are needed. This is the desktop confirmation path. The CLI's `close-plan` already puts the branch in its plan revision, and that protection has to stay.

### 2. P1: `dropStash` can remove the wrong stash and then fail to put it back

Location: `src/stash.ts`, `dropStash()`, the positional `git stash drop` and the `git stash store` that is meant to undo a wrong drop. Desktop, phone and loomctl all call it.

`dropStash` finds the selected commit's place, `stash@{n}`, and git drops that place. Another worktree's push can put a different stash there first. The current code reads which commit went and stores it back, but that store can fail, and a process stopped between the drop and the store has the same result.

Reproduced case, with the actual `dropStash` and real Git: stash A, selected by its commit. Just before the real positional `git stash drop`, another worktree pushes stash B, so the drop removes B. After that drop succeeds, `.git/refs/stash.lock` is held while the compensating `git stash store` runs, and the store fails with "cannot lock ref 'refs/stash' ... File exists". A is still listed, B is gone from the list, and `dropStash` rejects. B's commit still exists, so the work can be recovered by hand, but it is out of the list and nothing points the user at it.

Another list-and-check before a positional drop still races. The selected entry has to be checked and removed under Git's own lock, or by something equally complete that cannot remove another stash and then depend on a later undo. `applyStash` keeps applying by commit.

### 3. P2: `resolveBase` can create a thread from a stale or unrelated fetched commit

Location: `src/main.ts`, `resolveBase()` and its use in `createThread()`.

After `git fetch origin <ref>` succeeds, `resolveBase` prefers `refs/remotes/origin/<ref>`, even when this fetch didn't update that tracking ref. Its fallback is `FETCH_HEAD`, which any concurrent fetch in the repository overwrites.

Reproduced cases, real Git and the actual functions:

- A clone where `origin/feature` is feature v1 and there is no local `feature`. `remote.origin.fetch` is narrowed to `+refs/heads/main:refs/remotes/origin/main`, and origin's `feature` moves on to v2. `createThread` with base `feature` fetches v2, and `FETCH_HEAD` is v2, but the worktree starts at v1 because `origin/feature` still says v1.
- A `--single-branch --branch main` clone with no `origin/feature`. After the fetch of `feature`, another real `git fetch origin main` runs before the resolver reads `FETCH_HEAD`. `resolveBase` returns main's commit instead of feature's.

The fetch should land in a destination ref private to this one call, and the thread should start from the commit read from it. A remote-only base and the branch-name collision handling have to keep working.

Finding 2's regressions are Rust tests of the new native command, which didn't exist before the fix, so the before-evidence is the scratch run of the review's case against the old TypeScript `dropStash`. The same case (B pushed after A is picked and before the drop) is one of the Rust tests. Holding the lock is what makes the drop atomic: while Loom holds `refs/stash.lock`, any git that would push, drop or store a stash fails or waits, so the entry Loom finds is the entry it removes, and there is no undo to fail. The list changes in one rename. A Loom stopped before it leaves the list whole; one stopped after it has dropped only that entry. A Loom killed while holding the lock leaves `refs/stash.lock` behind, and git stash then refuses everywhere until it is deleted, the same as after a git killed mid-drop. A reftable repository is refused.
