# Make Loom easier to trust daily

October 11, 2026. Source snapshot `ac726f7`.

**For your daily workflow, build diff comments that you can send to an agent, then repeatable worktree setup and visible check results. For a public product, prioritize first-launch guidance and supported Windows releases.** These tracks share a purpose: make it easier to start useful work and decide what to do with the result. Loom already has substantial agent supervision, Git controls, and phone access. Its next useful additions should connect those capabilities. Safe local landing and a durable next-task queue are worthwhile later, but their failure cases make them larger projects than their buttons suggest. Public demand remains unproven, so test the existing product with outside Windows users before committing to collaboration or hosted execution.

## Loom already has the foundation worth extending

Loom has grouped worktree threads, multiple agent providers, waiting-agent cards, guarded replies and menu choices, bulk prompts, Git Changes, durable task IDs, and session restoration. Its phone app already includes Changes, Usage, Settings, dictation, and image attachments. Another dashboard or basic mobile control would repeat existing work. The useful question is where people still copy information, repair setup, or inspect terminals to understand an outcome. ([Current capabilities](<C:/Users/ayoub/Videos/claude/loom/README.md:98>), [phone capabilities](<C:/Users/ayoub/Videos/claude/loom/README.md:256>), [task commands](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:9510>))

The market comparison supports this focus. Conductor documents workspace setup and review workflows. Superset documents lifecycle scripts that can hold agent startup until setup succeeds. Warp and Claude Code both offer phone or browser control of local agent sessions. Phone access alone is therefore a weak product pitch. A stronger hypothesis is: **supervise several local coding agents on Windows, review their changes, and answer them from your phone.** Superset explicitly excludes Windows in its installation documentation, while Conductor directs users to a Mac installation. That establishes a relevant segment, not an exclusive market or a measured opportunity. ([Conductor workflow](https://www.conductor.build/docs/first-workspace), [Superset setup](https://docs.superset.sh/setup-teardown-scripts), [Warp remote control](https://docs.warp.dev/agents/cli-agents/remote-control), [Claude Remote Control](https://code.claude.com/docs/en/remote-control), [Superset installation](https://docs.superset.sh/install))

Your history gives the personal track clearer constraints. You asked for a phone interface adapted to mobile use, rejected the window mirror, and expressed a preference for no hosting fees. Preserve that deployment option. Keep phone dictation: the October 7 request supersedes the earlier suggestion to remove it. These are personal preferences and actual requests, not evidence about what future customers will buy. ## Close the daily review and setup gaps first

**Diff feedback should be the first addition.** On the desktop or phone, select a changed line, write a note, and send a batch to a chosen agent. Today Loom already renders numbered diff rows and has guarded submission; the missing piece is collecting the review and carrying its context into the prompt. Include the file, old or new side, line, selected excerpt, and diff revision. Preview the batch before sending. If the diff changes, flag the affected notes as stale. The risk is sending correct feedback against the wrong revision or pane. Measure the steps and elapsed time between noticing a problem and submitting its fix request. Conductor already documents this interaction, which supports its usefulness as a familiar workflow, without proving demand among Loom users. ([Diff rows](<C:/Users/ayoub/Videos/claude/loom/src/gitparse.ts:104>), [phone diffs](<C:/Users/ayoub/Videos/claude/loom/src/remote/changes.ts:406>), [guarded submit](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:9334>), [Conductor diff comments](https://www.conductor.build/docs/reference/diff-viewer))

**Worktree setup comes second.** Save one setup command per project and run it in a visible shell before the coding agent starts. If setup fails, keep its output and offer retry or explicit continuation. Copy ignored files only through an explicit selection with path and link validation. A fresh thread should reach its first useful edit without a conversation about missing dependencies. Loom currently adds the worktree and opens its panes immediately, so this extends a clear boundary. Repository commands and copied secrets require deliberate configuration. Measure how many new worktrees need manual repair and time to the first useful edit. Add port allocation only after simultaneous development servers produce real collisions. ([Thread creation](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:7121>), [pane launch](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:7150>), [shell receipts](<C:/Users/ayoub/Videos/claude/loom/README.md:639>))

**Recent tasks with check evidence should make results understandable.** Start with a drawer over the existing task journal: task, pane, outcome, time, uncertainty, and a link to the surviving session. Then attach one configured project check command, its exit result, output, and the code state it checked. The display must distinguish "agent turn completed," "check passed," "check is current," and "human review pending." None implies the next. A HEAD hash alone misses uncommitted changes; use an appropriate worktree fingerprint and invalidate evidence when relevant files change. If code changes during the check, do not present its result as current. Measure terminal reopening to discover what ran, and whether users can identify which code passed which command. ([Task semantics and fields](<C:/Users/ayoub/Videos/claude/loom/src/task.ts:1>), [history commands](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:9528>), [retention](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:4485>))

This task view can ship before check capture. It must explain that Loom retains the last 500 finished tasks and does not archive every original answer. Task records store prompt hashes and lengths, so the UI cannot promise historical prompt text from that journal. Avoid invented task titles derived from hashes. Existing context can provide labels where available. ([Stored task fields](<C:/Users/ayoub/Videos/claude/loom/src/task.ts:158>))

**Base progress and shared-file warnings should follow.** Remember the base when creating a thread, show how far it has fallen behind, and identify changed paths shared with other active threads in that repository. For example, two agents editing `src/main.ts` should be visible before landing either branch. Current upstream comparisons do not cover every unpushed branch. A shared path signals coordination risk, not a certain merge conflict. Handle rebases, renamed files, deleted refs, and uncommitted work without excessive polling. Measure whether warnings lead to useful coordination and record false alarms. ([Thread state](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:5687>), [Git status and polling](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:6964>))

## Land and queue work only after their failure paths are clear

**A local Land action fits your historical workflow.** Its smallest complete version checks the destination checkout and current Git state, accepts only a fast-forward, and preserves a recovery path. Require current check evidence when configured. Keep optional cleanup separate and offer it after landing succeeds. Revalidate refs, working files, and active writers immediately before mutation. Ignored-file collisions deserve explicit protection because ordinary Git safeguards are insufficient for that case. Recent deletion hardening covers concurrent checkouts, locks, and junctions; reusing those protections matters more than reducing Land to one merge command. Measure manual landing steps eliminated and unexpected cleanup or recovery events. Any lost work fails the feature. ([Git operations](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:8974>), [deletion protections](<C:/Users/ayoub/Videos/claude/loom/src-tauri/src/deletion.rs:92>), [previous landing proposal](<C:/Users/ayoub/Videos/claude/loom/docs/improvement-study.md>))

**One durable next task is the right first automation.** Queue a review prompt after a named implementation task completes. Show the pending prompt and destination, allow cancellation, and stop for failure, cancellation, approval, or unknown outcomes. At dispatch, recheck the session and input guards. Restart and retry must not send the prompt twice. This can eventually support review and fix sequences, but completion must never trigger automatic acceptance of the patch. Measure duplicate dispatches, unexpected destinations, and manual watcher interventions. ([Submission guards](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:9334>), [task journal](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:4296>))

The queue changes Loom's privacy design. Durable future prompts require storing text that today's hash-only task journal deliberately omits. Decide where that text lives, how long it remains, how cancellation deletes it, and what diagnostics exclude before implementing persistence. This is a reason to scope the feature carefully, not to hide the issue behind a generic automation editor. ([Task storage fields](<C:/Users/ayoub/Videos/claude/loom/src/task.ts:158>))

## Public adoption needs a successful first session

**First-launch checks and redacted diagnostics are the first public addition.** Detect Git and selected agent CLIs, explain missing or unknown compatibility, and guide the user into one existing checkout. Report phone setup stages separately: local server, Tailscale exposure, pairing, and reachability. Command availability does not prove authentication works. Export useful versions and statuses without prompts, credentials, or unreviewed logs. Opening an existing worktree folder is already possible; bulk discovery would improve convenience, not introduce worktree support. Measure the proportion of first sessions that reach a successful task without maintainer help. ([Requirements](<C:/Users/ayoub/Videos/claude/loom/README.md:12>), [opening threads](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:5695>), [remote status](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:9793>))

**Supported release delivery belongs beside onboarding.** Publish versioned Windows installers, show the installed version and release notes, and provide a clear update and rollback path. The README describes an unsigned installer and a checkout-based update command. Restart-to-update already exists; the missing product work is dependable delivery to ordinary users. Investigate executable signing and update-package verification separately. Preserve active sessions, avoid forced restarts, and handle app and `loomctl` version mismatches. Measure clean-machine install, update, and recovery success. Source inspection did not verify external release infrastructure or the installed binary's signature. ([Installation and updating](<C:/Users/ayoub/Videos/claude/loom/README.md:19>), [Tauri configuration](<C:/Users/ayoub/Videos/claude/loom/src-tauri/tauri.conf.json:41>), [restart handling](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:8827>))

**PR and CI status should be an optional public pilot.** Show a GitHub PR link, review state, and checks for the exact branch head in Changes. Open failed logs in the browser. Keep feedback forwarding explicit. Loom's current Create PR action pushes a branch and opens GitHub's compare form; it does not retain a PR object or fetch checks. Authentication failures, unavailable networks, forks, and stale results are part of the scope. Measure missed feedback and browser switching among testers who already use PRs. The earlier personal study deferred this because of local landing habits. That is not a reason to exclude future users' workflows. ([Current PR action](<C:/Users/ayoub/Videos/claude/loom/src/main.ts:6933>), [Conductor Checks](https://www.conductor.build/docs/reference/checks))

Build in phases without a calendar promise. First, release diff feedback and setup for daily use while preparing first-launch checks and supported distribution. Next, add recent tasks and current check evidence, then base warnings. Choose Land or a next-task queue after observing which manual handoff costs more effort. Land depends on trustworthy Git preflight and optional check evidence; the queue depends on restart-safe dispatch and an explicit prompt-storage policy.

For public validation, observe five Windows users install Loom and complete a real task without intervention, then run a two-week trial. Include people using multiple providers and people working through PRs. Record setup failures, return use, phone use, review friction, and what they still open another tool to do. Ask what they would give up or pay for, but treat stated interest separately from repeated use. This small pilot tests the product hypothesis; it cannot establish market size.

Defer cloud runners, multiplayer, an embedded IDE, generic automation graphs, and more visual themes. Revisit ports when servers collide and cross-agent handoff when users repeatedly change providers mid-task. These are scope choices, not permanent user vetoes.

This study combines source inspection, session history, and five competitors' official documentation checked on October 11. It includes no runtime tests, installation trials, customer interviews, or measured savings. Any implemented UI changes still require tests against the served build across desktop and phone widths.
